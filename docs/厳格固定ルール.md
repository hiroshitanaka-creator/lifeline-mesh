# 厳格固定ルール（Single Source of Truth）

この文書は、Lifeline Mesh リポジトリで今後の作業を判断する**最優先ルール**です。迷った場合はこの文書に従います。

## 1. 目的（何を守るリポジトリか）

- このリポジトリは、**災害時・インフラ劣化時でも通信できる、オフライン前提の E2E 暗号メッセージング**を実装・維持する。
- 仕様（`spec/`）・実装（`app/`, `crypto/`, `tools/`）・公開ドキュメント（`README.md`, `docs/`）の整合を守る。
- 利用者の安全性と、検証済み変更のみを mainline に収束させる運用を守る。

## 2. 優先順位（常に上から優先）

1. **安全性（Security / Safety）**
2. **mainline 収束（壊れていない状態を維持）**
3. **配布整合（README・docs・実装・テストの一致）**
4. **新機能追加**

上位の優先順位を損なう変更は、下位目的のために実施しない。

## 3. PR 運用ルール

- **1PR = 1トピック**。
- 変更は小さく、review 可能な単位に分割する。
- 目的外のリファクタ・文言修正・依存更新を同一 PR に混在させない。

## 4. 必須検証コマンド

PR 作成前に、少なくとも以下を実行して結果を確認する。

```bash
npm run test
npm run validate
```

補足:
- 本リポジトリでは `npm run validate` が `lint + typecheck + test` を実行する。
- 失敗時は、失敗理由を `docs/status.md` に記録し、未解決のまま mainline へ流さない。

## 5. README / status / phase progress の整合ルール

- 事実の起点は次の順で同期する。
  1. 実装・テスト結果（一次情報）
  2. `docs/status.md`（現状スナップショット）
  3. `docs/PHASE_PROGRESS.md`（存在する場合。中期進捗）
  4. `README.md`（対外向け要約）
- README の進捗・テスト記載は、`docs/status.md` と矛盾させない。
- `docs/PHASE_PROGRESS.md` が存在しない場合は、`docs/status.md` を進捗の基準文書として扱う。

## 6. 禁止事項

- 未検証（テスト未実行・失敗放置）の変更を mainline に流さない。
- `README.md` だけ先行更新し、実装・検証結果・`docs/status.md` を追随させない運用をしない。
- 実測していない数値（テスト件数・カバレッジ・性能）を推測で記載しない。
- 仕様に影響する変更を、対応する spec / docs 更新なしでマージしない。
