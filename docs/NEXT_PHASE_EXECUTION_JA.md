# Lifeline Mesh フェーズ実行計画（Phase 1〜10）

このドキュメントは、完成（1.0）までのフェーズを「実行可能なタスク」まで落とした計画です。
まずは要望に応じて **Phase 1〜5** を具体化し、そのうえで **Phase 6〜10**（安定成長フェーズ）を後続計画として整理しています。

## 方針

- **安全性を最優先**: 新機能よりも、暗号・可用性・誤操作耐性を優先する。
- **オフライン現場適合**: 災害現場での低帯域・高遅延・断続接続を前提に設計する。
- **段階リリース**: 1フェーズごとに受け入れ基準（Exit Criteria）を満たして次へ進む。

---

## Phase 1: アーキテクチャ整流化（基盤統一）

### 目的
- UI/ストレージ/モジュール境界を整理し、修正の波及リスクを下げる。

### 実行タスク
- [x] `app/index.html` の業務ロジックを `app/src/main.js` 側へ集約し、二重実装を解消。
- [x] `app/src/db.js` と `crypto/store.js` の責務を明文化し、公開APIを一本化。
- [x] 共通ユーティリティ（ステータス表示、エラーフォーマット、時刻処理）を抽出して重複排除。
- [x] モジュール依存図（どこがどこを呼ぶか）を `docs/` 配下に追加。
- [x] 破壊的変更を避けるための移行手順（旧UI→新UI）を手順書化。

### マイルストーン
- 実行パスが「UIエントリ → サービス層 → crypto/store」に統一される。
- 同一機能の重複実装が解消される。

### Exit Criteria
- 主要フロー（鍵生成/暗号化/復号/BLE送受信）で旧コード参照が残っていない。

---

## Phase 2: 品質保証強化（テスト駆動の回帰防止）

### 目的
- 変更時の不具合混入を早期検知し、リリース速度と安全性を両立する。

### 実行タスク
- [ ] E2Eを「要素存在確認」から「実データ往復検証」へ拡張（鍵生成→暗号化→復号）。
- [ ] BLE/Transportの失敗注入テスト（欠損chunk、切断、再送）を統合テスト化。
- [ ] CIで `lint + typecheck + unit + integration + e2e` を必須ゲートに統一。
- [ ] 失敗時アーティファクト（スクリーンショット/trace/log）保存をワークフローへ追加。
- [ ] テスト命名規約と flaky 対応手順（再実行条件・原因分類）を定義。

### マイルストーン
- 主要ユースケースの自動テストが常時通過。
- 不具合再発時に原因追跡可能なログが残る。

### Exit Criteria
- 重要機能に対する自動テストの欠落領域が「許容範囲」まで縮小している。

---

## Phase 3: コア機能補完（グループメッセージ統合）

### 目的
- 実装済み暗号モジュールをアプリ体験へ統合し、実運用価値を高める。

### 実行タスク
- [ ] `crypto/group.js` と UI を接続し、グループ作成/送信/受信/復号を実装。
- [ ] グループ状態（メンバー、sender key version、既読）をストアへ永続化。
- [ ] メンバー変更時の sender key ローテーションを自動化。
- [ ] グループ向けエラー表示（鍵不整合、バージョンずれ、復号失敗）を整備。
- [ ] グループ機能の単体・統合テストを追加（連続ラチェット、再参加、鍵更新）。

### マイルストーン
- グループ基本操作がUI経由で完結する。
- sender key運用が手動介入なしで回る。

### Exit Criteria
- 1対1メッセージと同等レベルで、グループ送受信が安定動作する。

---

## Phase 4: 通信信頼性強化（BLE/フォールバック運用）

### 目的
- 不安定通信環境でも「届く可能性」を最大化する。

### 実行タスク
- [ ] BLE送信の再送・ACK・タイムアウト設定を運用しやすいパラメータへ整理。
- [ ] 切断復帰時の outbox 再送戦略を実装し、重複送信抑止を検証。
- [ ] BLE失敗時に clipboard/file/QR へ自動または半自動フォールバック。
- [ ] ブラウザ/OSごとのBLE挙動差分を検証し、サポートマトリクスを文書化。
- [ ] 通信状態をユーザー向けに可視化（接続中/再送中/待機中/失敗）。

### マイルストーン
- 回線不安定時でも再送で回復する割合が改善。
- BLE非対応端末でも代替経路で運用継続できる。

### Exit Criteria
- 切断・再接続・欠損パケットのシナリオでメッセージ到達性が担保される。

---

## Phase 5: リリース運用整備（1.0前提の運用品質）

### 目的
- 開発チーム依存を下げ、誰でも安全にリリース/運用できる状態にする。

### 実行タスク
- [ ] リリースチェックリスト（品質・互換性・セキュリティ）を正式運用化。
- [ ] DB移行・障害対応・ロールバック手順をRunbookとして整備。
- [ ] 脆弱性対応フロー（検知→評価→修正→告知）の責任分担を明確化。
- [ ] 監視指標（失敗率、再送成功率、暗号エラー率）の収集方針を定義。
- [ ] リリース判定会（Go/No-Go）の固定アジェンダと承認者を設定。

### マイルストーン
- リリース作業がチェックリスト駆動で再現可能になる。
- 重大障害時の復旧手順が演習で検証済みとなる。

### Exit Criteria
- 「担当者が変わっても」同じ品質でリリース/復旧できる。

---

## Phase 6: 現場運用最適化（Reliability & UX Hardening）

### 目的
- 実運用での失敗率を下げ、非技術ユーザーでも迷わない操作導線にする。

### 主要タスク
- 受信トレイ/送信キューの状態表示を「未送信・再送中・配信済み・失敗」で統一。
- 失敗時ガイダンス（次に押すべきボタン、代替経路、再試行条件）をUIに標準表示。
- 長文・大容量メッセージ時の分割表示と進捗UIを改善。
- 災害時向けプリセット文面（安否、物資、避難、医療）をテンプレート化。

### マイルストーン
- 主要ユーザーフローの操作ミス率をベースライン比で低減。
- 失敗時の再送成功率を計測し、閾値をクリア。

### Exit Criteria
- 代表的な手動シナリオ（平常/不安定回線/切断復帰）で手順逸脱なく完遂できる。

---

## Phase 7: 配布・導入性強化（Adoption Readiness）

### 目的
- 団体・自治体・コミュニティが導入しやすい配布形態を整える。

### 主要タスク
- オフライン配布キット（静的ファイル一式 + 検証手順）を整備。
- 署名済みリリースアセットとチェックサム検証手順を標準化。
- 「初回起動5分で使える」導入ガイドをロール別（運用者/利用者）で作成。
- 多言語ドキュメントの優先言語を定義し、更新フローを確立。

### マイルストーン
- 新規ユーザーがガイドのみで初回送受信を完了できる。
- リリース検証手順が第三者でも再現可能。

### Exit Criteria
- 導入手順の外部レビュー（第三者）で重大な詰まりポイントがない。

---

## Phase 8: 相互運用・外部連携（Interoperability）

### 目的
- リレー手段の多様化に対応し、環境依存を下げる。

### 主要タスク
- トランスポート抽象に沿って外部連携アダプタ（例: ファイル中継拡張）を追加。
- メッセージエクスポート/インポート仕様を固定し、互換テストを追加。
- バージョン差分（旧クライアント）との互換ポリシーを明文化。

### マイルストーン
- 2種類以上の転送経路で同一メッセージ互換が確認できる。

### Exit Criteria
- 互換性テストスイートがCI常時通過。

---

## Phase 9: セキュリティ継続強化（Continuous Security）

### 目的
- 「一度作って終わり」ではなく、継続的に安全性を維持する。

### 主要タスク
- 依存ライブラリ更新の定期サイクル化と脆弱性SLA運用。
- 重要コンポーネント（鍵管理、復号フロー、ストア移行）の再監査。
- セキュリティ回帰テスト（既知攻撃パターン）を追加。
- 事故対応Runbook（鍵漏えい疑い、端末紛失、誤配信）を実地演習ベースで更新。

### マイルストーン
- 既知高リスク項目の対応時間短縮。
- 監査項目の定量トラッキング開始。

### Exit Criteria
- セキュリティ運用が属人化せず、定例プロセスとして回っている。

---

## Phase 10: 1.0 リリース判定

### 判定観点
- **機能完成度**: コア機能・運用機能・復旧機能が揃っている。
- **品質**: 単体/統合/E2E/互換テストが安定通過。
- **運用可能性**: 非開発者が手順に沿って導入・利用・復旧できる。
- **セキュリティ**: 既知重大リスクが許容レベル以下。

### Go/No-Go 基準（例）
- 重大不具合（P0/P1）が0件。
- リリースチェックリスト100%充足。
- 手動運用訓練シナリオを規定回数パス。

---

## 推奨進め方（実務）

- 1フェーズを**2〜3週間**で運用し、最後にレビュー会を固定開催。
- 各フェーズで「実装タスク」と「運用ドキュメント更新タスク」を必ずセット化。
- 次フェーズ開始条件は、前フェーズのExit Criteria達成 + 残課題の優先度再評価。
